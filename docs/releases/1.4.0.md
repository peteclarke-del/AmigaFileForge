# Amiga File Forge 1.4.0

CD support. Amiga File Forge can now open an ISO, read the Amiga metadata a
disc carries, recognise the AmigaOS 3.5 and 3.9 release CDs, and boot a
prepared drive with one of them attached.

Upgrade if you hold any Amiga material on CD. Nothing in this release changes
how an existing image is read or written, so there is no reason to upgrade in a
hurry if you do not.

## Opening a CD

A disc opens as an ordinary read-only pane and browses like any other image.

It is read from the file rather than loaded into memory. These images run to
hundreds of megabytes and the AmigaOS 3.9 disc alone is close to five hundred,
so listing a drawer should not cost half a gigabyte of resident memory. An ISO
is random access by construction, and this reader treats it that way.

Three naming schemes had to be reconciled, because the discs this was written
for use all of them. The base tree holds upper-case names with a `;1` version
suffix nobody wants to read, Joliet publishes long names in a second tree, and
Rock Ridge publishes them in an `NM` entry on the ordinary record.

Preferring Joliet is the usual choice and it is the wrong one for Amiga discs.
The Amiga extension hangs off the base tree, so reading the AmigaOS 3.5 disc
through Joliet gave a listing that looked perfect and had quietly dropped the
protection bits and comments from all six thousand of its files. The base tree
wins here whenever it carries Rock Ridge, and Joliet is the fallback for a disc
mastered for other systems.

That extension, `AS`, is why this is not a generic ISO reader. It holds the
protection bits and the comment, so a file copied off a CD arrives with what
the disc gave it rather than with defaults.

The reader is bounded against a damaged or hostile image. Continuation chains,
directory sizes, entry counts and nesting depth all have limits, symbolic
parent paths are refused, and a directory extent that never terminates ends the
walk instead of looping.

Reading the real discs was checked by hand against 7-Zip, and every extracted
file matched byte for byte.

## Installing AmigaOS 3.5 or 3.9

These releases are not installed the way 3.1 is, and this release does not
pretend otherwise. The disc carries a Commodore Installer script that runs on
the Amiga, reads the versions of the libraries the live system has loaded, asks
a great many questions and patches an existing installation in place. It says
of itself that pretend mode cannot be used with it, and 3.9 refuses outright
unless it finds an earlier release to update. There is no unattended path, and
inventing one would produce a drive that does not boot.

What can be done from outside the Amiga is everything up to that point, and
each part of it otherwise costs an operator a long detour to find out.

The disc is identified by the volume name Commodore wrote, `AmigaOS3.5` or
`AmigaOS3.9`, then confirmed by looking for that release's own drawer, so a
contribution CD carrying a similar name is not accepted on the name alone.

The processor is checked against the hardware profile rather than discovered by
booting. Both releases need a 68020 or better. An A1200, A3000, A4000 or CD32
qualifies on its own, and so does any machine carrying a 68020 to 68060
accelerator or a PiStorm. A stock 68000 machine is refused with a reason saying
what to change.

The drive is checked too. Both releases update a system rather than creating
one, so a volume with no `S:Startup-Sequence` has nothing for them to update.
That is the case this application can fix itself, by installing Workbench 3.1
from your own floppies first.

Every blocking reason is reported at once. Fixing one, running again and being
told the next is the slow loop a preflight exists to prevent.

## Switching on the CD driver

Attaching the disc was not enough on its own, and the symptom would have been
the worst kind: a machine that boots perfectly and shows no disc at all.

A stock Workbench 3.1 installation has everything needed to read a CD and none
of it switched on. The Extras disk puts the filing system in `L:`, and the
Storage disk puts the `CD0` mountlist in `Storage/DOSDrivers`, which is the
drawer Workbench keeps things in until they are wanted. AmigaDOS reads only
`Devs/DOSDrivers`, so the driver sits there present and inactive. This was
found by installing Workbench from real 3.1 floppies and looking at what
landed.

Booting with a CD now activates it. Commodore also leaves the mountlist's
`Device` and `Unit` lines commented out and takes them from tooltypes on the
`CD0` icon, defaulting to a real SCSI drive at unit 2, which nothing emulated
answers. Those two lines are written into the mountlist itself, in the form the
file's own comment documents, and every other field Commodore shipped is
carried across untouched.

Activating the driver writes to the image, so booting with a CD is treated as
an image change and takes an undo checkpoint before it runs. The preflight says
what will happen before it happens.

One value is unproven and is documented as such. The device the mountlist is
pointed at, `uaescsi.device` unit 0, is what FS-UAE presents a CD on for a
machine with no CD drive of its own. Only a real boot settles that. If the disc
does not appear, the value lives in `Devs/DOSDrivers/CD0` on the drive and can
be edited there. The
[install guide](../INSTALL-GUIDE.md) says where to look.

## Two faults fixed along the way

Both predate this release and affected more than CDs.

The breadcrumb bar split paths on a full stop, which is RISC OS syntax rather
than AmigaDOS. A drawer named `OS-Version3.5` became two crumbs, neither of
which was a real path and neither of which navigated anywhere. Any Amiga drawer
with a full stop in its name was affected. It splits on `/` now, and the root
is written as the bare colon AmigaDOS uses.

Capacity was read by asking the AmigaDOS engine to stat the image, which
refuses a disc with no AmigaDOS filing system on it. A CD listed nothing at
all as a result. A disc reports itself as full and read-only instead.

## Repair and format behaviour

No format restriction has changed, and no image written by 1.3.1 is read
differently by 1.4.0. CDs are read-only: nothing here writes an ISO.

## Linux packages

The release provides packages for Debian 13 and Ubuntu 24.04 on AMD64, ARM64
and ARMv7. Choose the file matching both the operating system and processor.
For example:

```bash
sudo apt install ./amiga-file-forge_1.4.0-1~deb13_amd64.deb
```

The packages include the native GTK launcher, desktop integration and the
bundled HxCFloppyEmulator runtime for HFE and SCP media, as they did in 1.3.1.

Installing 1.4.0 over an earlier release preserves native XDG workspace data
and Docker working volumes. Save important open images before upgrading.

See the [installation guide](../INSTALLATION.md) and
[Linux desktop guide](../LINUX-DESKTOP.md) for setup and troubleshooting.
