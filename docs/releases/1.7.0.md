# Amiga File Forge 1.7.0

Large drives. A hard drive can now be any size up to 2 TB, laid out in a
partition editor, in the filing systems large Amiga partitions use, and
carrying the handlers the machine needs to mount them. A card attached through
USB can be prepared where it is, or have an image written to it.

Before this release a partitioned drive was created with one FFS partition,
the FFS formatter stopped at about 50 MB, and nothing here could add a
partition or put an image on a card.

## Creating a drive

**File → New → New Image → Partitioned drive · HDF with RDB** opens a partition
editor. Give the drive a size, such as `128GB`, and lay out its partitions: a
device name, a volume name, a filing system, a size, a boot flag and a boot
priority for each. A partition with no size takes what the others leave.

The layout is checked after every change. The bar under the table shows the
drive as it would be divided, and anything that stops the drive being made is
said beneath it.

| Filing system | DOS type | Largest partition | Handler |
| --- | --- | --- | --- |
| Professional File System 3 | `PFS\3` | 1.6 TB | Comes with Amiga File Forge |
| Professional File System 3, direct SCSI | `PDS\3` | 1.6 TB | The same file |
| Smart File System | `SFS\0` | 127 GB | Supplied by you |
| FFS and OFS | `DOS\0` to `DOS\5` | 4 GB | In Kickstart |
| FFS Long Filenames | `DOS\7` | 4 GB | In the Kickstart of AmigaOS 3.1.4 and later |

- A **starting layout** and the **filing system for its large partitions** are
  offered and not chosen for you.
- An FFS partition is kept to 4 GB. FFS is slow to validate and easy to damage
  past that, and the FastFileSystem in a Kickstart 3.1 ROM cannot reach further.
  The editor refuses a larger one and names the Professional File System.
- `PFS\3` suits a machine whose device driver reaches the whole drive:
  AmigaOS 3.1.4 or later, a PiStorm, an accelerator with its own driver, or an
  emulator. `PDS\3` talks to the drive directly, which is how a machine with
  the `scsi.device` of Kickstart 3.1 reaches a partition past the first 4 GB.
  The layout says which partitions that affects.
- Sizes are counted in powers of 1024. A card holds less than its label says,
  so **Or size it for a card** fills in a size that fits, and lists any card
  attached through USB at its exact size.

A drive image is a sparse file. A new 128 GB drive is made in under a second
and takes a few megabytes, and about 40 MB with Workbench installed onto it.

A raw drive image can also hold one PFS3 or SFS volume with no partition table,
and a hardfile or raw image can be made in any FFS or OFS variant.

## Filing-system handlers

Kickstart carries the FastFileSystem and nothing else. Every drive made here
is given the handlers its partitions need, in the Rigid Disk Block, so a drive
with PFS3 partitions boots on a machine that has never had PFS3 installed.

`pfs3aio` 19.2 comes with the application, under its BSD-4-Clause licence. Any
other handler is supplied through **Tools → Filing-system handlers…**, from a
file or from a drive that already carries one.

Where a supplied handler is kept follows how the application was installed. A
copy installed for one person keeps it for that person. A copy installed for
the whole machine, from the Debian or RPM package, keeps it in
`/var/lib/amiga-file-forge/handlers` for everyone who uses the machine, and the
desktop application asks for an administrator's password to do so. The Docker
service keeps it in its working volume.

## Changing the partitions of a drive

**Tools → Partitions…** shows the partition table, the room no partition uses
and the handlers the drive carries. A partition can be added in unused room,
formatted in any filing system, renamed, made bootable or removed. A drive
image can be made larger, and a card larger than its partition table says can
have the rest of it claimed. Partitions are not moved or resized.

On an image each change is one undo point. On a drive opened in place there is
no undo, and the dialog says so first.

## Real cards, in the Linux desktop

- **Initialise…**, in the **Open attached drive** list, partitions and formats
  a card in place and opens it for writing, so Workbench and software are
  installed straight onto it. Only the blocks that describe the drive are
  written, so a 128 GB card is ready in seconds.
- **File → Write image to attached drive…** writes only what the image holds,
  then reads it back from the card and compares. **Write every byte** writes
  the empty space as well.
- **File → Save drive image to a file…** saves a drive, one partition or a
  volume wrapped in a partition table, without its empty space. **Save image**
  does the same of its own accord for a drive image of 2 GB or more.

A card is named again in a confirmation before anything erases it.

## Saving a large drive from the browser

The browser edition, which is what the Docker service provides, reads every
byte of a drive to build the download, the empty space included. That takes
about a quarter of a minute for each gigabyte of the drive's size, which is
over half an hour for 128 GB. The download itself is small.

The New Image dialog says so while a drive of 2 GB or more is being laid out.
**Save image** asks first, with the size and the time it will take, and saves
nothing if the answer is no. Creating the drive and working in it are as quick
as on any other.

## Repair and format behaviour

These changes affect how images are written:

- **The Rigid Disk Block follows the Amiga includes.** Releases up to 1.6.0
  recorded the vendor text and the number of the last table block in the wrong
  fields, and left out the cylinder limits. Partitions mounted, but HDToolBox
  showed nonsense for the drive. A drive written by an earlier release is
  still read correctly, and is put right the first time its table is changed.
- **New partitions use a `MaxTransfer` of `0x1FE00`**, which is what the IDE
  ports of an A600, A1200 and A4000 need. The earlier `0xFFFFFF` is the classic
  cause of silent corruption on real hardware.
- **Export as → Partitioned drive** makes a partition of exactly the volume's
  size. It used to round up to a whole cylinder, which moves where the
  FastFileSystem looks for the root block. It also adds the handler a PFS3 or
  SFS volume needs.
- **A new drive is described in cylinders of one mebibyte** from 1 GB up, and
  in the 16 heads and 63 sectors every emulator assumes below that.
- **A large volume is not cleared when it is formatted.** Volumes up to 64 MB
  are cleared from end to end as before. A larger one has only the blocks that
  describe it written.
- **Both hard drive conversions** are offered for volumes up to 4 GB, because
  they are handed to the browser as one download. The desktop application's
  save converts a larger one.

Writing files to a Smart File System volume of many gigabytes is also much
faster. Placing one file read every bitmap block of the volume, which took
four seconds a file on 100 GB.

## How this was checked

A 128 GB drive built here, with Workbench 3.1 installed onto a PFS3 partition,
was booted on an emulated A1200 with Kickstart 3.1. The handler was loaded from
the drive. `PFS\3`, `PDS\3` and FFS partitions all mounted, and what the
machine then wrote to each of them read back and validated here. An FFS
partition placed 100 GB into the drive was unreadable under Kickstart 3.1,
which is what the layout warns about.

amitools, an independent implementation, reads the partition table and
validates FFS volumes that use bitmap extension blocks.

Not yet checked: a Smart File System partition on the real SmartFilesystem
handler, `PDS\3` on the `scsi.device` of a real Kickstart 3.1 machine, and a
physical card, which was stood in for by a file.

## Linux packages

The release provides packages for Debian 13 and Ubuntu 24.04 on AMD64, ARM64
and ARMv7. Choose the file matching both the operating system and processor.
The Debian 13 AMD64 package downloads as:

```bash
sudo apt install ./amiga-file-forge_1.7.0-1.deb13_amd64.deb
```

The packages include the native GTK launcher, desktop integration, the udev
rule for attached drives, the PFS3 handler, and the bundled HxCFloppyEmulator
runtime for HFE and SCP media. A package installed from 1.5.0 or later can also
update itself from **Help → About Amiga File Forge → Check for Application
Updates**. Installing 1.7.0 over an earlier release preserves native XDG
workspace data and Docker working volumes. Save important open images before
upgrading.
