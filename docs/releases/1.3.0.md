# Amiga File Forge 1.3.0

Amiga File Forge 1.3.0 prepares the drive as well as filling it. A blank
partition is not a machine you can use, so this release installs AmigaOS onto
one from your own Workbench floppies, and moves staging onto the drive being
built rather than into a directory on the computer running the application.

It also fixes two defects that between them stopped file imports working at all
in the ordinary case. Anyone using 1.2.0 to put files on a partitioned hard
drive should upgrade.

## Importing files did nothing, and said nothing

Choosing **Insert File** and selecting files opened the compatibility review,
and accepting it wrote nothing. The review decides whether to continue from a
named submit button, and `new FormData(form)` leaves the submitting button out
of the form data, so the choice read back as `null` and every selected file was
abandoned at that step without a message.

The same review gates file imports, folder imports, disc images and
cross-format transfers, so all four were affected and all four are fixed.

Inserting a disc image into a partitioned hard drive had a second problem: it
never offered to extract or install the disc, and stored the ADF as an ordinary
file instead. The decision asked whether the image's own kind was `ffs`, and a
hard drive answers `hdf` whichever volume is open, so the case the install
modes exist for was the one case that fell through. Five places asked that
question and all five now ask whether the pane is showing a volume.

## Installing Workbench onto a drive

**Tools -> Install Workbench** prepares the open partition from the floppy
images of the AmigaOS release you own. Point it at the folder holding them, or
pick the images by hand.

No AmigaOS is shipped or downloaded, and none can be: it is not free to
redistribute. ADF, ADZ, DMS and HFE images are all read.

Disks are recognised by the **volume name inside each image** rather than by its
file name. ADF collections are named inconsistently, and a renamed file says
nothing at all about its contents, while the volume name was written by
Commodore and travels with the data. That is what lets a folder be pointed at
rather than a set assembled by hand, and anything in it that is not part of a
release is listed as ignored rather than quietly installed.

The release is decided once, from the Workbench disk, and every other disk is
matched to it. Mixing releases is the classic way to end up with a drive that
looks complete and boots to a Guru, so a disk from another release is left out
rather than mixed in. Where a collection holds several dumps of one disk, one
that says it was verified is preferred and one that says it was modified or
cracked is avoided.

Each disk lands where the AmigaOS install script would put it: Workbench and
Extras merge into the root, and Fonts, Locale, Storage, Classes, Backdrops and
Install become drawers of their own. The copy order is fixed rather than
incidental, so the Workbench disk's full `C:`, `L:` and `Libs:` are not
overwritten by the cut-down copies Extras and the Install disk carry. `T`,
`Trashcan`, `Devs/DOSDrivers` and `Prefs/Env-Archive` are created afterwards
because the install script makes them and no disk provides them.

Files already on the volume are left alone. A drive you have already
partitioned, named and put work on is added to rather than replaced, and
installing twice does not undo hand edits made in between.

Two limits are reported rather than worked around. A hard drive boots from the
flag in its Rigid Disk Block, which this cannot yet set, so an unmarked
partition is named as one that will not start. The drawers the install creates
have no icons, so software installed into them is reachable from a Shell rather
than from the desktop. Both are recorded in the [backlog](../BACKLOG.md).

## Staging goes onto the drive

Staged discs are now written into a drawer on the target image, not into a
directory on the machine running Amiga File Forge. The point of staging is that
the install can be finished where the title will actually run, and a host
directory is unreachable from an emulator and from real hardware, which is
exactly where it is wanted. Boot the drive, open the drawer, and run the
title's own installer against it.

The staged list is read back off the drive rather than out of a record kept by
the application, so a drive built on another machine, or one whose staging
notes were deleted, still reports what is sitting in its staging drawer.

Protection bits and comments are written onto the volume with the files, so the
`.inf` sidecars staging used to write are no longer needed. Installing a staged
title is a move within one volume rather than a second copy, which means the
protection bits, comments and datestamps the discs carried are the ones already
there.

The staging drawer is `Storage/Install`. `Storage` is where Workbench keeps
what is not in use yet, which is what a staged set is. A plain `Install` drawer
at the volume root was the obvious choice and turned out to be taken: a
Workbench install copies the AmigaOS Install disk there, and sharing the drawer
listed that disk's own `c` and `Libs` as though they were staged titles.

`AMIGA_INSTALL_STAGING_DIR` no longer has any effect and can be removed from
existing deployments. Anything staged by 1.2.0 remains on the host in the
directory it named; copy it into the drive by hand, or stage the discs again.

## Menus and dialogs

Menus close when the pointer moves off them, when something outside them is
clicked, on Escape, and when a command inside them is chosen. Until now a menu
stayed open until its own heading was clicked again, which covered the file
list while the operator was working somewhere else.

The dialogs have been made consistent with each other. Two rules that several
dialogs were written against had no styling at all, so a field hint or a
two-column row rendered at browser defaults beside controls that did not, and
a text area sat unstyled next to styled inputs in the same dialog.

The nineteen remaining `confirm`, `alert` and `prompt` calls have been replaced.
Native browser dialogs cannot be styled or themed, ignore the application's
typography, and cannot be told apart from a web page pretending to be the
operating system, which is the wrong impression for a tool that writes to disk
images. The replacements layer over an open dialog or over the page, which is
the reason the file and hex editors had reached for the native ones: a second
dialog cannot be opened over one that is already showing.

## Repair and format behaviour

No format restriction has changed, and no image written by 1.2.0 is read
differently by 1.3.0. Installing Workbench and installing a staged title both
use the existing volume-write path, the same filename policy and the same
loader repair as a plain copy.

Staging now takes an undo checkpoint, because it writes onto the drive being
built rather than onto the host. Installing Workbench, installing a staged
title, installing WHDLoad and adding a slave each take one as they did before.

## Internal changes

Staging and the Workbench install were the same code twice. They were written
separately, came out almost identical, and had already drifted: one warned about
a file it could not read and carried on, the other raised and discarded
everything it had copied. Both go through one implementation now, and an
invariant test keeps them there.

The progress callback every long-running operation accepts had been written out
identically in eighteen modules, and now has one definition.

## Performance record

The full benchmark profile for this release is attached to the GitHub Release
as `benchmark-full-1.3.0.json`.

The paths those figures cover are unchanged by this release. Installing and
staging write through the same volume-write code as 1.2.0; what changed is
where staging puts its output, not how a volume is written.

## Linux packages

The release provides packages for Debian 13 and Ubuntu 24.04 on AMD64, ARM64
and ARMv7. Choose the file matching both the operating system and processor.
For example:

```bash
sudo apt install ./amiga-file-forge_1.3.0-1~deb13_amd64.deb
```

The packages include the native GTK launcher, desktop integration and the
bundled HxCFloppyEmulator runtime for HFE and SCP media.

Installing 1.3.0 over 1.2.0 preserves native XDG workspace data and Docker
working volumes. Save important open images before upgrading.

See the [installation guide](../INSTALLATION.md) and
[Linux desktop guide](../LINUX-DESKTOP.md) for setup and troubleshooting, and
the [install guide](../INSTALL-GUIDE.md) for preparing a drive and installing
floppies onto it.
